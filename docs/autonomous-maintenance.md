# 初回導入後の自律保守

初回設定で対象、権限、予算を固定し、以後の通常のルール保守は人間の指示・承認を待たず進める。
LLM の起動には保存済みの ChatGPT ログインを使い、OpenAI API キーを追加しない。
利用先は、ルートに Go module が１つ、または指定ディレクトリに Python/uv か Node.js/npm のパッケージが１つあるリポジトリである。

## 実行の分担

| 実行箇所 | 処理 |
| --- | --- |
| AGENTS.md | 開発開始時にルールと適用状態を確認し、終了前に検証する手順を持つ |
| .claude/rules/dev-standards-agent-harness.md | Claude の実装依頼を、受入条件の承認後に agent-harness へ渡す |
| SessionStart と UserPromptSubmit | ルールの状態と必要な対応を現在の LLM に渡す |
| Stop | 現在のファイルに対応する検証記録がなければ、検証を要求する |
| CI | LLM の報告とは独立して生成物の欠落・変更、静的解析、整形、テストを検証する |
| 週次の遅れ検知 | タグを付けた版が利用先に届いていないことを、資格情報なしで知らせる |
| ローカルの定期保守 | 共通ルールの改善、検証、自動マージ、利用先への反映を担当する |

hooks は `.codex/hooks.json` に固定し、ルール更新ごとに書き換えない。
Codex の仕様上、初回にはプロジェクトと hook 定義の信頼設定が必要である。
hooks が利用できない環境でも AGENTS.md と CI、定期保守が機能する。
保守用の Codex 子プロセスでは hooks を無効にして、保守の再帰起動を防ぐ。

## 初回のホスト設定

開発ツールを準備し、実行ファイルをビルドする。

```sh
mise run bootstrap
mise run check
codex login status
bin/dev-standards host-init --fleet .local/maintenance/fleet.json
```

Windows の実行ファイル名は `bin/dev-standards.exe`。
チェック用の npm ツールは mise の `npm.package_manager = "npm"` でインストールし、OS 間で依存関係の配置方法を揃える。
`host-init` はリポジトリの origin を保守元として記録し、キャッシュに固定した起動口を配置する。
台帳を既に作成している場合は上書きしない。
ChatGPT ログインの認証情報はコピーせず、Codex 自身の保存済み認証を利用する。

台帳はホスト専用の非公開データであり、Git に追加しない。
初期値は１回の実行1,800秒、変更32ファイル、提案ファイルの合計1,200行、修復２回まで。
共通ルールの正本と実行処理はリポジトリで版管理し、この台帳は実行場所と許可範囲だけを持つ。

## 利用先の初回導入

言語選定記録を作り、利用先で次を実行する。
台帳の場所はホスト設定で作成したファイルを指定する。

```sh
dev-standards onboard --repo /path/to/project --decision decision.md --fleet /path/to/dev-standards/.local/maintenance/fleet.json
```

Python/uv では `--profile python-uv --component-path session-indexer` を追加する。
Node.js/npm では `--profile node-npm` を追加する。Go/Swift を併設する場合は README の宣言を作り、
`--companions companions.json` を追加する。英語の共通指示には `--instruction-language en` を使う。AGENTS.md を rulesync で生成している場合は
`--instructions rulesync` も追加し、適用後に `rulesync generate` で AGENTS.md を再生成する。
既存の予約タスクは先に移行し、Python と uv は完全な版番号で固定する。

`onboard` は初回適用、既存指示の保持、hooks と CI の配置、CLI キャッシュの準備、台帳への登録を行う。
導入後の宣言、正本、生成物を通常の初回導入変更としてコミットし、利用先の既定ブランチに反映する。
既に0.1系の設定がある場合も、保存した前回出力を照合して移行する。
既存の AGENTS.md と hooks は固有の正本へ保存し、共通の入口と合成する。
Claude 向けのルールも配置し、同名の未管理ファイルがあれば衝突として停止する。
ハーネス本体と認証は別途準備する。詳細は README の「Claude からの実装依頼」を参照する。

最初の登録先を先行適用対象にする。
初回に対応できない構成や衝突があれば、その時点で理由を示し、既存の設定を破棄しない。
初回設定後の利用先は台帳から発見されるため、普段の機能開発で保守を指示する必要はない。

## 通常開発の確認

```sh
mise run standards:prepare
mise run standards:version
mise run standards:verify
mise run standards:finish
```

設定だけでなく、Git 管理ファイルと追跡対象になる新規ファイルの内容から検証対象を識別する。
採用ルール、HEAD、ファイルが変わった場合と、24時間を超えた記録は再検証する。
検証中に入力が変わった場合も成功記録を作らない。
Stop hook の継続要求は１回に制限し、解決しない問題は未検証として記録する。

保守で既定ブランチに反映済みの変更は、次の開始時に既定ブランチの作業ツリーがクリーンで、
fast-forward できる場合だけローカルに取り込む。
検証には採用版と一致する保存済み実行ファイルを使い、固定した hook の起動口は書き換えない。
未コミットの作業がある場合はその作業を保持し、現在の採用版で開発を続ける。
作業中の checkout に reset、stash、強制 push は行わない。

共通の問題を見つけた LLM は、次の入口から観測だけを保存する。

```sh
dev-standards feedback --rule CORE-FORMAT --message '同じ整形条件の矛盾を複数のタスクで確認した。'
```

同じ観測は重複させず、秘密情報に見える文字列は記録を拒否する。
会話全文を共通ルールに追加しない。

## 定期保守の実行

```sh
bin/dev-standards maintain --fleet .local/maintenance/fleet.json
```

このコマンドを、既存ログインを使うローカルの定期タスクから呼び出す。
このチャットでは Codex アプリの定期実行を接続する。
PC が停止している間は実行できないため、再び利用可能になった実行で保守を進める。
台帳内の対象を処理するので、リポジトリごとの定期タスクは不要。

処理は次の順で進む。

1. 保存済みの ChatGPT ログインと、台帳の権限・予算を確認する。
2. 別の checkout で共通基盤を取得する。
3. 週１回、または新しい観測がある場合に、Codex が共通ルールを見直す。
4. 変更範囲と必須条件を機械的に検証する。
5. 静的解析、テスト、race 検出、脆弱性検査を実行する。
6. 別の読み取り専用 Codex 実行で、変更内容と根拠をレビューする。
7. 更新 PR の対象コミットの CI 成功を確認し、人間の承認待ちにせずマージする。
8. マージ後の CI 成功も確認して版を付け、検証した CLI を保存する。
9. 先行対象から順に移行し、新規 checkout の bootstrap と宣言済みのルール生成を済ませてから、検証、独立レビュー、自動マージ、マージ後の再確認を行う。
10. 成功した観測と処理結果を記録し、次の実行で重複処理をしない。

GitHub では通常の PR と CI を通す。既存のブランチ保護を無効化しない。
利用先のコミット形式は `.standards/mise.project.toml` の変数で指定できる。
指定がなければ従来の件名を使い、指定があれば自動コミットと更新 PR の題名に同じ件名を使う。
値はテンプレート展開しない、空でない256文字以内の1行の文字列である。

```toml
[vars]
standards_commit_message = "🔧 chore: 共通開発ルールを自動適用"
```

既存のコミットフックは実行し、形式検査を無効化しない。
共通設定 CI の成功後も、対象 HEAD に対する GitHub のマージ可能状態を確認する。
他の必須検査の集約ジョブがまだ作られていない間も、元の時間予算内で待機する。
待機中に HEAD が変わった場合や衝突・失敗が確認された場合は、マージしない。
既定ブランチや人の編集した自動更新ブランチに対して強制 push しない。
GitHub の操作には既存の GitHub CLI 認証と、そのアカウントに許可された操作を使う。
ブランチ保護が人間の承認を必須にしている場合、初回に自動保守用の運用条件を整える必要がある。

同時実行を排他し、処理時間に上限を設ける。
実行時間を超えて残った保守ロックは次の実行で回収する。
失敗した段階で通常展開を停止し、最後に成功した実行ファイルを維持する。
前回の停止理由は次回の見直しへ診断情報として渡す。
共通ルールに差分がない場合も、GitHub の取得元コミットの CI 成功を確認してから採用する。
マージ後の確認が途中で止まった場合も、次回は同じ検証済みコミットへのタグ付けを回復できる。
次回は新しい checkout から再試行し、人間にルール編集や PR 承認を依頼しない。
認証失効や利用枠不足は失敗として記録し、成功とは報告しない。

## 更新の遅れの検知

タグを付けた後に利用先への展開が失敗または中断すると、その利用先だけ古い版のまま残る。
そのため利用先には `.github/workflows/dev-standards-version-lag.yml` を生成し、毎週月曜 00:17（UTC）に版を確認する。
未適用の版のうち最も古いもののコミットから7日以上経っていれば、ジョブを失敗させて GitHub の通知で知らせる。
タグには時刻を記録していないので、経過日数はタグが指すコミットの日時から数える。
タグ付けがコミットより遅れた場合は、タグを付けてから7日未満でも失敗することがある。
版の取得は公開リポジトリのタグから Git だけで行い、権限は `contents: read` のまま secret も追加しない。

このジョブは確認だけを行い、PR の作成や更新はしない。更新は引き続き定期保守が担当する。
失敗したら保守ホストで `dev-standards maintain` の状態を確認する。
取得元に接続できない場合と公開された版が見つからない場合も失敗として扱い、確認できなかった回を成功にしない。

タグ付けも定期保守が行うので、保守全体が止まっていると新しいタグが増えず、このジョブは失敗しない。
PC の停止や認証の失効そのものは、この検知では分からない。

必須検査の workflow とは分けている。保守は対象コミットの `dev-standards.yml` の実行結果を待つため、
同じファイルで遅れを失敗にすると、その失敗で保守自身が止まるためである。
公開リポジトリの schedule は活動のない状態が60日続くと GitHub に無効化される。
無効化された利用先では検知も止まるので、Actions の画面から再度有効にする。

## 自律更新の範囲

保守エージェントが更新できる共通基盤の範囲は `rules/`、`guidance/`、`profiles/`、`templates/`。
利用先では `.standards` の正本と、そこから生成する設定・指示・CI を扱う。
業務コードやアプリのテスト、認証情報は保守の変更対象にしない。

初期の基本ルール７件の識別子、必須検査、エラー扱いと非免除の条件、
EditorConfig の必須動作は、保守ジョブ自身から緩和できない。
版番号の更新とタグ付けは、検証を通った保守処理が行う。
保守処理の実装、変更予算、検証コード、権限は自律更新の対象外にしている。

新しい言語の実行系や未知の検査方式を追加する場合は、対応する実装が必要。
共通ルールの通常の改善・廃止可能な説明の整理・テンプレートの更新は、
この範囲内で検証から適用まで自動で完了する。

## 検証

通常のテストは、Codex の応答を置き換えながら実際の Git リポジトリ、ビルド、検証、
ルール更新、タグ作成、利用先への反映、２回目の差分ゼロを通す。
GitHub API の待ち条件は、対象コミット・workflow・成功状態を照合するテストで確認する。

既存ログインの実機確認は、明示的に次を実行する。通常の CI では推論を呼ばない。

```sh
DEV_STANDARDS_LIVE_TEST=1 go test ./internal/automation -run TestCodexSavedLoginLive -count=1 -v
```

ローカル台帳の `.local/maintenance/latest.json` に、実行結果、更新コミット、
検証済み実行ファイルの場所を保存する。変更がない回の個別通知は不要。

利用先の展開途中で停止した場合、同じ保守元コミットを確認して展開を再開する。
再開の途中では新しいルール提案を始めず、未処理の観測は次の見直しまで保持する。
未実装の機能を、文書の要求追加だけで実装済みの保証として扱わない。

マージ後 CI の確認中に時間切れになった場合は、確認待ちの保守元コミットを記録する。
次回はそのコミットの検証と CI 確認から再開し、確認が済むまで採用成功としない。
差分がない利用先でも、対象コミットの共通設定 CI 成功を確認する。

対象の保守元コミットは利用先の展開前にも永続化し、全件が完了するまで保持する。
見直しを実行しなかった再開処理では、週次見直しの最終実行時刻を更新しない。
