# Claude と Codex の開発ハーネス設計

人間は Claude と要件を決め、実装担当がサンドボックスで実装し、別のモデルがレビューして、条件を満たせば自動でマージする。
このリポジトリに限らず、Mac で開発する複数のリポジトリで使う。

全体の流れは [構成図](2026-11-07-claude-codex-harness.infra) に Omnodi の DSL で記録する。

## 目的

- 人間の確認を、受入条件とセキュリティ関連に絞る。
- セキュリティを担保したうえで、通常の実行では人間の認証を求めない。
- 実装の品質を測り、結果に応じて実装担当のモデルとエフォートを変えられるようにする。

## 対象外

- iPhone からの監視。必要になった時点で Tailscale などを使って別途実装する。
- 自律保守（`dev-standards maintain`）の変更。経路を分けて共存させる。
- 自動デプロイのあるリポジトリでの初期運用。導入段階 3 で扱う。

## 役割と権限

| 担当 | 役割 | 秘密情報 | GitHub の操作 |
| --- | --- | --- | --- |
| 人間 | 受入条件の承認、停止した PR の判断 | 個人の Vault を含むすべて | すべて |
| Claude（要件定義） | 要件と受入条件の整理、ハーネスの起動 | なし | 読み取りのみ |
| 実装担当 | worktree 内の編集と検証 | なし | なし |
| レビュー担当 | 差分と受入条件の照合、判定 JSON の出力 | なし | なし |
| ハーネス | 差分の取り込み、検査、push、PR、記録、マージ、revert | 専用 Vault の読み取り | GitHub App の権限内 |

ハーネスは内容を判断しない決定的なスクリプトである。
判断は LLM、合否の適用はスクリプトに分ける。

実行画面は Herdr で確認する。
Herdr の状態表示は誤判定があり得るので、完了や合否の判断には使わない。
Herdr がなくてもハーネスの判定は変わらない。

## タスクの流れ

1. Claude が要件と受入条件を整理し、人間が承認する。
2. ハーネスが実行 ID を発行し、実装担当の触れない専用 clone と、そこから複製した作業用 clone を `<repo>-worktrees/agent-<run_id>` に作る。`git worktree` は `.git` を共有するので使わない。
3. ハーネスが `hc run --bg` で実装担当を起動する。実行ファイルは絶対パスで解決する。
4. 実装担当がサンドボックス内で実装と検証を行い、`.agent-run/result.json` に結果を書く。このディレクトリは `.git/info/exclude` で管理対象から外す。
5. ハーネスがサンドボックス内で差分を出力し、専用 clone に適用する。ハーネスの権限では作業用 clone の Git を操作しない。
6. ハーネスが秘密情報スキャンとセキュリティ関連パスの検査を行う。
7. ハーネスが専用 clone でコミットして `agent/<run_id>` に push し、PR を作る。PR 本文に受入条件を記載する。
8. GitHub の CI 成功を待つ。
9. 未解決のスレッドを確認する。外部レビューの完了は、設定したリポジトリでだけ待つ。
10. ハーネスがレビュー担当を起動し、基準ブランチの checkout から差分を読ませる。
11. ハーネスが判定 JSON と SHA を確認し、修正を依頼済みのスレッドを解決して、次のコマンドで auto-merge を有効にする。

```sh
gh pr merge --auto --squash --match-head-commit <SHA>
```

レビューの結果は、対象 SHA のステータス `agent-review` に記録する。
レビュー担当のモデルが変わっても同じ名前を使う。

### 受入テストの固定

受入条件をテストで表せる場合は、Claude（要件定義）が受入テストを書き、人間が承認してから実装を始める。
このテストを固定対象として実行記録に残す。
実装担当が固定対象のテストを変更または削除していたら、ハーネスは停止する。
テストの弱体化を差分レビューだけに任せないためである。

テストで表せない受入条件は、レビュー担当が差分と照合する。

### 完了の判定

`hc wait` は利用上限や信頼確認の待機を失敗として返さないことを確認済みである。
次の順に判定する。

1. `.agent-run/result.json` が検証可能な内容で存在すれば、完了の申告として扱う。
2. `hc wait` がタイムアウトしたら `hc read` の出力から利用上限の文言を検査する。作業中の出力にも同じ語が出るので、画面が前回と変わっていないときだけ利用上限とみなす。
   端末の終了を検出したときは、待機中に書かれた結果がないかもう一度確認する。
3. 1 ラウンドの上限 1,800 秒を超えたら停止する。

完了の申告は信用しない。差分と検査結果で確認する。

### 修正の繰り返し

CI の失敗、外部レビューの指摘、レビュー担当の指摘は、実装担当に戻す。
修正は合計 2 回までとし、超えたら停止する。

### 外部レビュー

ハーネスの PR は CodeRabbit なしで運用する。CodeRabbit はシートのない GitHub App の PR をレビューしないためである。
レビューは別モデルの 1 段だけとし、外部レビューの完了は既定で待たない。

スレッドの解決を必須にしたリポジトリでは、未解決の指摘が残ると auto-merge が完了しない。
そこで、スレッドは毎回確認し、外部レビューの指摘があれば修正の入力として扱う。

| スレッド | 扱い |
| --- | --- |
| 許可した Bot の新しい指摘 | 実装担当に修正を依頼する |
| 修正を依頼済みで未解決のまま | レビュー担当に渡して解消を確認させ、合格後にハーネスが解決する |
| セキュリティまたは重大な問題の指摘 | 停止する |
| 人間のコメント、Bot を装った利用者のコメント | 停止する |

`external_review_check` を設定したリポジトリでは完了を待ち、check が 3 分以内に現れなければ未導入として進める。
スキップや上限到達でも check は `completed` になるので、この待機はレビューの実行を保証しない。
指摘の本文は信頼できないデータとして扱い、HTML コメントと折りたたみ部分を除いてから渡す。

### 同時実行

1 リポジトリにつき同時に 1 タスクとする。
排他により、PR 同士の組み合わせで壊れる問題と、基準ブランチの更新による再レビューを減らす。

## 自動マージの条件

次をすべて満たす場合だけマージする。

- 受入条件が人間に承認されている。
- 秘密情報スキャンで検出がない。
- セキュリティ関連パスと人間の確認が必要なパスに当たらない。
- 必須チェックが成功している。既定は `workflow-result` で、`.agent-harness/policy.json` の `required_check` で変更できる。ruleset の必須チェックと同じ名前にする。同じ名前のチェックが複数あれば、すべての成功を求める。
  1 ラウンドの上限までに完了しなければ停止する。マージ後の main の確認が上限までに終わらなければ、記録を残して次の実行か `reconcile` で確認し直す。
- レビュー担当が実装者と別のモデルで、判定が合格である。
- すべての受入条件がレビューで判定されている。受入条件は 1 行 1 条件とし、省略があれば停止する。
- セキュリティの指摘がない。
- 判定の SHA と PR の先頭 SHA が一致する。

`agent-review` は必須チェックにしない。
自律保守の `dev-standards/auto-*` と Renovate の PR には、レビューの実行役がいないからである。
ハーネスを通さない手動マージは防げないので、問題が起きた段階で必須チェック化を検討する。

### 人間の確認で止める変更

| 区分 | 対象 |
| --- | --- |
| セキュリティ（パス） | 認証・認可、秘密情報、実装タスクでの依存関係の追加、`.github/workflows/**`、ハーネス本体、`AGENTS.md`、`CLAUDE.md`、IAM などの権限設定 |
| セキュリティ（レビュー） | 入力検証の欠落、権限の問題など、レビュー担当が指摘したもの |
| 取り返しがつかない変更 | 破壊的な DB migration、Terraform の適用を伴う変更（`terraform-github` を含む） |
| 外部レビュー | 外部レビューのセキュリティの指摘、人間の未解決のコメント |
| 運用上の停止 | 修正回数の超過、テストの削除、固定した受入テストの変更、時間上限、判定の不正、SHA の不一致 |

パスの検査は基準ブランチにある定義を使い、PR 側の変更を読まない。
レビュー担当がプロンプトインジェクションで欺かれても、パスの検査は影響を受けない。

停止時は `needs-human` ラベルを付け、理由を PR に書く。通知は GitHub の通知を使う。

人間の確認を求める条件は、ハーネス側の定義に置く。
共通ルールには入れない。`internal/automation/maintain.go` の検査が、自律保守の共通ルール提案からこの種の条件を拒否するためである。

## セキュリティ

### 秘密情報の段階

| 段階 | 実行者 | 範囲 | 人間の認証 |
| --- | --- | --- | --- |
| 0. 秘密情報なし | 実装担当、レビュー担当 | 何も渡さない | 不要 |
| 1. 無人実行 | ハーネス | 1Password の専用 Vault `agent-harness` の読み取り | 不要 |
| 2. 人間の承認 | 人間 | 個人の Vault、セキュリティ関連 PR のマージ、権限の変更 | 必要 |

段階 1 の認証は次の順に進む。

1. macOS キーチェーンから 1Password のサービスアカウントのトークンを読む。
2. `op run` で専用 Vault から GitHub App の秘密鍵を取得する。
3. 対象リポジトリに限定した短命のインストールトークンを発行する。
4. このトークンで push、PR、ステータス記録、マージ、revert を行う。

サービスアカウントの条件は次のとおりとする。

- 権限は `read_items` だけとする。
- アクセスできる Vault は `agent-harness` だけとする。
- 90 日以内の有効期限を付ける。期限切れの場合はハーネスを停止する。

サービスアカウントの作成と GitHub App のインストールは、人間が行う。

GitHub App の条件は次のとおりとする。

- 権限は `contents`、`pull_requests`、`statuses` の書き込みと、`metadata`、`checks`、`actions` の読み取りに限る。
- `workflows` と `administration` の権限を付けない。
- 対象リポジトリだけにインストールする。
- ruleset のバイパス対象に入れない。

ハーネスは `~/.config/gh/hosts.yml` のトークンを使わない。

### 実装担当の分離

サンドボックスの権限プロファイルで次を強制する。

- 書き込みは worktree の内部だけとする。実装担当と検証のコマンドには、Go、uv、npm のキャッシュと Go のモジュールの保存先を worktree の `.agent-run/cache` に向ける環境変数を渡す。Go は既存のモジュールキャッシュを読み取り専用の proxy として先に使う。
- 通信はパッケージレジストリと公式ドキュメントだけを許可する。GitHub には接続させない。
- `~/.config/gh`、`~/.ssh`、`~/.codex/config.toml`、キーチェーンの読み取りを拒否する。
- パッケージや外部サービスのトークンを持つ `~/.npmrc`、`~/.netrc`、`~/.git-credentials`、`~/.pypirc`、`~/.docker`、`~/.kube`、`~/.gnupg`、`~/.config/gcloud` と、Codex の他のセッションの記録も拒否する。
- ドメイン制限が効かない MCP、Web 検索、プラグイン、アプリ、フックは無効にする。

### 実装担当の成果物を信用しない

実装担当が書いたコードは、次の場面でも実行され得る。

- **テストとフック:** ローカルの検証は、すべて実装担当と同じサンドボックス内で行う。ハーネスの権限で実行しない。
- **コミット:** 専用 clone で `core.hooksPath=/dev/null` としてコミットする。フックの検査はサンドボックス内で実行し、最終的な検証は CI に任せる。
- **差分の出力:** 作業用 clone の `git` はサンドボックス内でだけ実行する。Git の設定を書き換えられても、ハーネスの権限では実行されない。
- **差分の適用:** 専用 clone へ `git apply` で適用し、作業用 clone の `.git` の設定を引き継がない。
- **秘密情報スキャン:** 基準ブランチの設定と固定した版の `betterleaks` で差分を検査する。

### レビュー担当の分離

- 基準ブランチの checkout で動かし、PR 側の指示ファイルを読ませない。
- 差分はレビュー対象のデータとして渡す。
- ファイルの編集、シェル、ネットワークを使わせない。
- 出力は JSON スキーマで検証する。不正なら不合格として扱う。

### Claude（要件定義）の制限

権限ルールで `op read`、キーチェーンの読み取り、`gh pr merge` の直接実行を拒否する。
権限ルールはコマンドの文字列で判定するので、絶対パスや別のシェルを経由した実行は防げない可能性がある。同じユーザーで動く以上は完全な境界にならないので、影響を抑えるために専用 Vault の中身を最小限にする。

## 復旧

ハーネスは、自動マージした PR の main の CI を確認する。
デプロイ先を対象にした後は、スモークテストの結果も確認する。

失敗した場合は、次の順に処理する。

1. そのリポジトリの自動マージを止める。
2. revert PR を作成する。
3. CI が成功したら自動でマージし、人間に通知する。
4. 人間が原因を確認し、停止を解除する。

revert にはレビューを行わない。マージ前の状態に戻すだけだからである。
衝突や CI の失敗で revert できない場合は `needs-human` で止める。
修正の再実装は、人間の確認後に新しいタスクとして始める。

Mac が停止していた場合や auto-merge の待機が時間切れになった場合は、次回の実行か `reconcile` で、排他を取ったうえでマージの結果から確認する。
auto-merge を有効にする前に記録するので、その間に止まると auto-merge のない PR が残る。`reconcile` はこれに `needs-human` を付け、有効にし直さない。人間が外した可能性があるためである。
作成済みの revert PR があれば作り直さず、そこから再開する。

## 利用枠

実装担当かレビュー担当の利用枠が上限に達したら、全体を止めて作業用 clone を保持する。
解除後に同じプロファイルで再開する。
レビュー担当の上限で止まった場合は、push と PR が済んでいるので、再開時はレビューからやり直す。

例外として、`run` に `--codex-auth api-key` を明示したときは、Codex の実装を OpenAI の API キーで実行する。
既定は ChatGPT ログインのままで、上限に達しても自動では切り替えない。
キーは専用の `CODEX_HOME` に置き、`~/.codex` と自律保守から分離する。
予算の上限は OpenAI のプロジェクトで設定する。ハーネスは費用を制御しない。

別のモデルへの切り替えと、同じモデルによるレビューは行わない。
評価の記録が混ざることと、相互チェックの保証が弱くなることを避けるためである。

## プロファイルと評価

実装担当は、エージェント、モデル、エフォートの組み合わせ（プロファイル）で指定する。
既定は Codex の `gpt-6.1-sol`、`medium` とする。
レビュー担当は、実装者と別のベンダーのモデルを自動で選ぶ。

初期の比較対象は次の 3 つとする。

| エージェント | モデル | エフォート |
| --- | --- | --- |
| Codex | `gpt-6.1-sol` | `medium` |
| Codex | `gpt-6.1-sol` | `high` |
| Claude | `claude-opus-5-5` | 既定 |

評価は次の 3 段階で行う。

| 段階 | 内容 | 実施時期 |
| --- | --- | --- |
| 1. 実行記録 | 全 PR で、プロファイル、タスク種別、受入条件の初回合否、修正回数、停止理由、人間の介入、所要時間、マージ後の revert を記録する | 常時 |
| 2. 過去 PR の再現 | マージ済み PR の直前のコミットから各プロファイルに実装させ、実装者に見せないテストで判定する。1 課題につき 2〜3 回実行する | モデル更新時や、記録に変化が出たとき |
| 3. 人間の目視 | どの実装か伏せて、差分を少数だけ読み比べる | 段階 1 と 2 で差が出ないときだけ |

タスク種別は新機能、バグ修正、リファクタリングの 3 種類とする。
過去 PR の再現は、公開された振る舞いを確認するテストがある PR を 5〜10 件選ぶ。

総合点は作らず、指標を並べて判断する。
既定のプロファイルは、差がはっきりした場合だけ変える。

実行記録は `~/.local/state/agent-harness/runs/<run_id>.json` に保存し、Git に追加しない。

## auto-merge の経路

| 経路 | 対象 | レビュー | 扱い |
| --- | --- | --- | --- |
| 本ハーネス | 実装タスク | 別モデル | 新規 |
| 自律保守 | `dev-standards/auto-*` | Codex の別実行 | 変更しない |
| Renovate | 依存関係の更新 | CI のみ | 変更しない |
| `claude-auto` ラベル | Claude が作成した PR | なし（ラベルで承認） | 対象リポジトリでは使わず、廃止は別の PR で扱う |

## 導入段階

1. **基盤の検証:** 検証項目を確認する。Codex の利用上限の解除後（2026-11-09 5:54）に通しで試す。
2. **初期運用:** `tqer39/agent-telemetry` で実行する。デプロイのワークフローがなく、テストがあり、`allow_auto_merge` が有効である。
3. **対象の拡大:** 自動デプロイのないリポジトリに広げる。デプロイ先は、スモークテストと自動 revert が揃ってから対象にする。
4. **配布:** 動作が安定してから `dev-standards` の配布に載せる。CLI の動作変更には、初回適用、再適用、衝突、失敗時の回帰テストを追加する。

不具合がすり抜けたら、原因を検査かレビュー観点として 1 つ追加する。

## 将来の候補

### Pi

[Pi](https://pi.dev/) は、次の条件を満たしてからプロファイルとして追加する。

- コンテナなどの隔離環境で実行する。Pi には組み込みのサンドボックスがない。
- 短命の認証情報を使う。
- Anthropic の第三者ツールに関する規約と、OpenAI の認証方式を一次情報で確認する。

最初に試す場所は、過去 PR の再現とする。Pi Durable は experimental なので、制御基盤には使わない。

### `agent-review` の必須チェック化

ハーネスを通さないマージが問題になった場合は、自律保守と Renovate を除外できる方法を検討する。

### 最新 main での検証の必須化

`strict_required_status_checks_policy` は有効にしない。
有効にすると、自律保守の `waitMergeReady` が `BEHIND` のまま時間切れになるおそれがある。
同時実行の排他とマージ後の自動 revert で扱い、PR の組み合わせによる障害が実際に起きた場合に検討する。

### Actions でのレビュー

Mac の停止が運用の問題になった場合は、ステータス名を変えずに GitHub Actions へ移す。
その際は Claude の認証方式、利用枠、ワークフローの自己改変の対策を確認する。
