# dev-standards: 実装の委譲

このファイルは dev-standards が管理する。個人設定やスキルの追加は不要。
このリポジトリに `AGENTS.md` や `.standards/rules.md` があれば、それらも読む。

## 適用する依頼

ユーザーから機能追加、不具合修正、リファクタリングなどの実装を依頼されたら、
`agent-harness` の名前がなくても、以下の手順で Codex に実装を委譲する。
Claude は要件と受入条件の整理を担当する。
質問、調査、レビューだけの依頼には適用しない。
dev-standards が管理する共通ルール・設定の導入、更新、保守にも、この委譲手順を適用しない。
ユーザーから直接依頼された場合も既存の共通保守手順に従い、追加の承認を待たずに進める。
ユーザーが Claude 自身による実装やハーネスを使わない方法を明示した場合は、その指定に従う。
ハーネスのレビュー担当や、自律保守の担当として起動された場合は、渡された役割だけを行う。
別のハーネスを再帰的に起動しない。

## 実行手順

1. 要件を整理し、検証できる受入条件を作る。必要な受入テストも準備する。
2. 受入条件と受入テストをユーザーに示し、承認を得る。
   単なる実装依頼を受入条件の承認とは扱わない。実行前に、ハーネスが実装・レビューから
   条件を満たした PR の自動マージまで進めることを説明する。
3. `agent-harness` が PATH 上にあることを確認する。
   ユーザーが実行ファイルの場所を明示した場合は、その場所を使ってよい。
   対象の GitHub リポジトリと基準ブランチを確認し、`agent-harness doctor --repo <owner>/<name>`
   で前提条件を検査する。現在のハーネスは macOS 用で、Codex、Claude、GitHub、1Password の
   CLI と事前の認証・権限設定が必要。未導入や検査失敗の場合は理由を報告して止める。
4. ハーネスはリモートから別の作業用 clone を準備する。現在のワークツリーの未コミット変更を
   自動では引き継がない。既存変更の続きを依頼された場合は、基準にするリモートブランチと
   変更の取り込み方を確定してから実行し、既存変更を破棄しない。
5. タスクと承認済み受入条件をファイルに書き、実際の値で次を実行する。
   テストを差分で準備した場合は `--acceptance-patch <patch-file>` も付ける。

   ```sh
   agent-harness run --repo <owner>/<name> --base <base-branch> \
     --title '<変更の題名>' --kind <feature|bugfix|refactor> \
     --task-file <task-file> --criteria-file <criteria-file> --approved-by-human
   ```

6. 終了コードと実行状態を確認し、実装・レビュー・マージの到達点を正確に報告する。

`--approved-by-human` は、この会話で受入条件が承認された場合にだけ付ける。
API キーによる従量課金の指定はユーザーが明示した場合に限る。
失敗、利用枠待ち、人間の判断待ちでは、理由を報告して止める。
無断で Claude 自身の実装に切り替えたり、`clear-stop` や `gh pr merge` を直接実行したりしない。
